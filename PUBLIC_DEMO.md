# Douyin Studio public service

The public web app is isolated from the owner engine: the app binds only to `127.0.0.1:8766`; the owner service stays at `127.0.0.1:8765` and is not routed through Cloudflare Tunnel. Public sessions, jobs, uploads, and outputs live under `public-demo-data/`. The public interface accepts local file uploads only. The jobs API rejects `url` and `link` sources with `400 unsupported_source`; no public job starts a downloader. Previously stored jobs/files are retained.

## Current service

- A single job runs at a time. Up to ten more jobs may wait. Each browser session may have one active/queued job; session, IP, and global rate limits apply.
- The worker accepts video from 30 seconds through 2 hours. It checks the complete uploaded file with `ffprobe` before creating the job.
- Uploads are chunked at 16 MiB and can resume after reselecting the same file in the same browser session. The server reports the current upload offset. The hard upload ceiling is 8 GiB; each request uses the smaller live limit derived from free disk space, a 10 GiB disk reserve, active-job storage, and pending uploads.
- Jobs are allowed up to six hours, scaled down for shorter videos. Each job can reserve up to 28 GiB for inputs, working files, and output; the service caps its own occupied storage at 32 GiB and retains a 10 GiB free-space reserve. The owner can delete completed/blocked/cancelled jobs to reclaim disk.
- Finished outputs remain until the owner deletes them or storage capacity blocks new jobs. No fixed one-day output expiry is configured.
- Only uploads are accepted. Uploaded media is checked by `ffprobe` for a duration from 30 seconds through 2 hours before a job enters the queue. The API no longer accepts Douyin URLs; the standalone downloader module and its package are not called by the public service.
- Queue size is one running plus up to ten waiting; another request is rejected with HTTP 429 when full. ETA uses completed-job history when available and shows the sample count; with no history it falls back to the per-job runtime limit and is labeled conservative. The only completed timing sample is a 301-second video processed in 422.2 seconds. In a simulated position-10 scenario with one running job and nine earlier queued jobs, all 2 hours long, the history-based estimate was about 28 hours 3 minutes to start the target and about 2 hours 48 minutes to process it. With no history, the runtime-limit fallback gives a conservative 60-hour wait. These are queue calculations, not a 2-hour benchmark.
- MP4 preview, Range, and download intentionally return application code `video_delivery_unavailable` (HTTP 403) through Quick Tunnel. Subtitle/SRT delivery remains available. The 403 is generated by `public_demo.py`; it is not evidence of a Cloudflare-generated block. Do not route MP4 through Quick Tunnel or rename files to bypass Cloudflare video-delivery terms.

## Start and stop

1. Run `start-public-demo.bat` to start the isolated service and check local health.
2. Run `start-public-tunnel.bat` to create a Quick Tunnel. Use only the URL currently written to `public-demo-url.txt`; it changes after restart. The current URL passed `/api/public/health` over HTTPS, and an external proxy probe also fetched that endpoint successfully. An earlier provisioning attempt returned HTTP 429, but a later attempt succeeded; do not reuse any URL from old logs or backups.
3. Run `stop-public-tunnel.bat` to stop public access while leaving both local services untouched.
4. Run `stop-public-demo.bat` to stop the Tunnel and the isolated public service. The owner service on 8765 remains running.

The Hanoi PC must stay powered on, awake, and online. A working Quick Tunnel URL is public to anyone who has it and has no login. Do not use it to distribute video as a production service: Cloudflare documents Quick Tunnels as test/development only, without an uptime guarantee, and says public hostname traffic is subject to its video-delivery terms. Free Cloudflare CDN/Tunnel delivery of MP4 from this private host is not a supported distribution plan. A private R2 bucket plus a Worker on `workers.dev` was evaluated but not provisioned; R2 overages can be billed and Cloudflare recommends production Workers use a route/custom domain rather than `workers.dev`.

Latest local measurements during the upload-only verification: 16,640 MiB RAM free, 686 MiB VRAM free, and 33,362 MiB disk free; current dynamic upload ceiling 7,803,663,701 bytes, with a 10 GiB free-disk reserve. The health check chose CPU fallback because VRAM was below the 1,800 MiB floor; 16,640 MiB RAM is above the 12 GiB CPU fallback threshold. Resource figures change with machine load. A 52.208-second video completed using the upload pipeline in 48.3 seconds and produced a 7,496,780-byte MP4 locally. This does not validate processing a 2-hour video.

## MP4 delivery design and cost

- Quick Tunnel is not an MP4 delivery path: it is temporary, has no uptime guarantee, supports at most 200 in-flight requests, and changing/stopping it changes or ends the URL. An earlier provisioning request returned HTTP 429 (`Tunnelstore request failed`); a later request succeeded and currently routes to port 8766.
- A possible domainless prototype is a private R2 Standard bucket with a Worker on `workers.dev`. The Worker would authorize a short-lived per-job capability, serve only that job's object (including Range), and use an R2 binding; browser clients would not receive R2 credentials or public bucket access. A hard 9 GB stored-object cap, 900,000 Class A operations/month, and an application-side read budget below 10 million/month could stay inside R2's published monthly free allowances. Workers Free has 100,000 requests/day and 10 ms CPU per request; over-limit Worker traffic fails rather than being a production guarantee. These caps are measurable but need to be enforced and monitored.
- R2 Standard includes 10 GB-month, 1 million Class A, and 10 million Class B operations/month, with free internet egress. Above that, Standard storage is $0.015/GB-month, Class A is $4.50/million, and Class B is $0.36/million; billing rounds usage upward. `r2.dev` is rate-limited and testing-only. `workers.dev` needs no custom domain, but Cloudflare recommends routes/custom domains for production rather than `workers.dev`.
- Cloudflare's video guidance identifies Stream or Enterprise Stream Delivery as the recommended paid video products; it does not certify public MP4 delivery through a Worker/R2 design as a compliant substitute. Stream's published pricing is $5/month per 1,000 stored video minutes and $1 per 1,000 delivered minutes. A single 2-hour stored video therefore needs the $5 storage increment; one complete 2-hour playback/download adds about $0.12. Viewers do not need Cloudflare accounts or a custom domain, but this fails the zero-cost requirement.
- Decision: **BLOCKER for policy-confirmed, dependable, zero-cost public MP4 delivery**. R2/Worker could be a capped free-tier experiment only after Cloudflare confirms the video-delivery policy applies to that architecture and account-side billing controls are understood. Nothing was provisioned or billed.

## Zero-cost private MP4 option

Cloudflare documents that media traffic over public Tunnel hostnames is subject to its video-delivery terms, while its private-network routes are exempt and intended for large files/high-traffic media. A potential $0 route is Cloudflare Zero Trust private networking with the remote user enrolled through the Cloudflare One Client; Cloudflare lists a Free plan for teams under 50 users. This requires installing the client, creating/enrolling users in a Zero Trust organization, and replacing public anonymous access with an authenticated private route. It does not meet a browser-only/anonymous requirement. It is not configured here. The app remains bound to loopback; any private-route connector or local proxy must preserve that boundary and must be explicitly tested before use. The alternative public Worker/R2 design is not treated as policy-approved video delivery; no R2 or Worker resources were provisioned.

The owner interface remains at `http://127.0.0.1:8765`; it is never exposed by the public Tunnel.
